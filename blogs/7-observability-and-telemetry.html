Where Did the Time Go? Step-Level Latency Tracing and Error Rates for a RAG Assistant

Category 7: Observability & Telemetry (#observability, #tracing). Feature covered: F9 (Distributed Tracing / Observability & Tracing).

"The assistant feels slow" isn't something you can fix. "Retrieval takes 120 ms and the LLM takes 2,400 ms" is. A RAG answer has two main steps — finding the right chunks and generating the reply — and when something is slow or broken, you need to know which one. F9 adds that visibility.

What F9 Measures

For every question, F9 (core/telemetry.py) records:

  • retriever_ms — time spent in the retrieval step.
  • llm_ms — time spent in the LLM step.
  • total_ms — wall-clock time for the whole call.
  • Calls and errors — running counts, from which an error rate is calculated.

These come back in every /ask response as a trace object (when METRICS is on), and are printed to the console when DEBUG_MODE is on:

[F9] Latency - retriever: …ms, llm: …ms, total: …ms
[F9] Error Rate - 0/12 calls (0.0%)

How It Works

1. A LangChain callback handler as a stopwatch

StepTimer extends LangChain's BaseCallbackHandler. LangChain fires events as a chain runs, and the timer listens to them:

  • on_retriever_start / on_retriever_end time the retrieval step.
  • on_llm_start / on_chat_model_start / on_llm_end time the LLM step. Chat models like ChatOpenAI fire on_chat_model_start instead of on_llm_start, so both are handled.

Measurements use time.perf_counter(), a high-resolution clock meant for timing.

2. Ambient registration, so nested calls are captured

Callbacks normally have to be passed into each invoke() call through its config. But the conversation-memory wrapper calls the inner chain without forwarding that config, so a timer passed the normal way would miss the real work.

F9 avoids that by using the same trick LangChain's own cost counter uses: the timer is stored in a ContextVar and registered with register_configure_hook(). LangChain then attaches it automatically to every chain run in the current context, however deeply nested.

3. A context manager that counts calls and errors

with trace_call(session_trace_totals) as timer:
    result = chain.invoke(...)
# timer.retriever_ms / timer.llm_ms / timer.total_ms are now filled in

trace_call() increments the call count, measures total time, and — if the wrapped call raises an exception — increments the error count before re-raising it. A finally block always records the total time and clears the timer.

Example

User: "What vegan options do you have?"

Answer: "Vegan options include the Sea Salt Edamame ($6.50), Spicy Garlic Edamame ($8.00), and the Yuzu Citrus Sorbet ($7.00) for dessert."

Response also includes: "trace": {"retriever_ms": …, "llm_ms": …, "total_ms": …, "errors": 0, "calls": …}

(In a typical run the LLM step is far larger than retrieval, which tells you where optimization effort should go.)

Honest Limitations

  • In-process, not distributed. The roadmap name says "distributed tracing," but F9 is step timing inside one Python process. It doesn't send spans to an external tracing tool such as Langfuse or LangSmith, and it doesn't follow a request across services.
  • Last step wins. Each *_end event overwrites the stored duration rather than adding to it. On a pipeline with several LLM calls — like the LangGraph engine's route, generate, and verify steps — llm_ms reflects the last LLM call, not the sum.
  • Counters reset on restart and, like F6's totals, aren't thread-safe under concurrent requests.

What's next (not yet built): exporting traces to a tracing platform such as LangSmith or Langfuse, summing durations across multiple LLM calls, and persisting latency alongside cost in the database. None of these is implemented in this project yet.
