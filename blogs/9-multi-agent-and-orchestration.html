One Interface, Many Engines: A Strategy Factory, a Parallel Entry Point, and a Self-Correcting LangGraph

Category 9: Multi-Agent & Orchestration (#agents, #strategy). Features covered: F12 (Strategy Factory Pattern), F12.1 (Parallel Entry Point), F13 (LangGraph State Machine Engine), F14 (CrewAI) and F15 (AutoGen) — planned, not yet built.

The first version of the assistant had exactly one way to answer a question: retrieve, then generate. That's fine until you want to try a smarter approach without breaking the one that works. This post covers how the project made "how a question gets answered" pluggable (F12), added a new entry point without touching the old one (F12.1), and built its first agentic engine — a graph that routes, verifies, and retries (F13).

Step 1: Build the Plug Before the Appliances (F12)

F12 (engines/base.py) applies the Strategy pattern: define one interface, and let each answering approach implement it.

class BaseMenuEngine(ABC):
    @abstractmethod
    def answer(self, cuisine: str, question: str, session_id: str,
               use_memory: bool = True) -> dict:
        """Returns {"result": str, "source_documents": [Document, ...]}"""
  • One return shape for every engine — the same shape LangChain's RetrievalQA returns — so callers never care which engine produced an answer.
  • A factory: get_engine("plain_rag") or get_engine("langgraph") returns the engine. Each is imported lazily and built only on first use, then cached and reused.
  • Shared building blocks: model selection (core/llm.py) and the retrieval pipeline (core/vectorstore.py's get_retriever()) were pulled out so every engine uses the same ones.
  • PlainRagEngine is the original retrieve-then-generate chain, re-implemented behind the interface.

Step 2: A Parallel Entry Point (F12.1)

The obvious move would have been to edit menu_api.py to call the factory. Instead, it was left completely untouched as a known-good baseline, and a new file, engine_api.py, was added beside it — the strangler fig approach: build the new path next to the old one and move traffic over when it's proven.

  • Same request shape, plus one optional field: engine, to choose an engine per request.
  • A default from configuration: DEFAULT_ENGINE in .env (defaults to plain_rag).
  • Visible in the response: every answer includes "engine": "plain_rag" or "engine": "langgraph".
  • The trade-off: the Google Sheets routing helpers are duplicated between the two files and have to be kept in sync by hand.
uvicorn engine_api:app --reload --port 8000

POST /ask {"cuisine": "sushi", "question": "What's in the Dragon Roll?", "engine": "langgraph"}

Step 3: An Engine That Checks Its Own Work (F13)

LangGraphEngine (engines/langgraph_engine.py) replaces the fixed two-step chain with a LangGraph StateGraph — a small state machine where each node does one job and edges decide what happens next.

            ┌──(off_topic)──▶ redirect ──▶ END
route ──────┤
            └──(on_topic)───▶ retrieve ──▶ generate ──▶ verify ──(grounded, or 2 attempts)──▶ END
                                 ▲                         │
                                 └────────(retry)──────────┘
  • route: a structured LLM call (RouteDecision) decides whether the question is about the restaurant at all. Off-topic questions go to redirect, which returns a polite message without spending any retrieval.
  • retrieve: the same shared hybrid retriever every engine uses.
  • generate: answers with the restaurant persona prompt. On a retry, it also receives the verifier's feedback ("Your previous answer was rejected: … Try again, using only the context below.").
  • verify: a second structured call (VerifyDecision) asks, "Is the answer fully supported by the context, with nothing invented?" and returns a yes/no plus its reasoning.
  • A bounded loop: if the answer isn't grounded, the graph goes back to retrieve and tries again — but stops after MAX_RETRIES = 2 attempts, so a hard question can't loop forever.
  • State, not memory: GraphState carries the question, documents, answer, verifier feedback, and attempt count between nodes during one request. Conversation memory across turns still comes from the shared memory module wrapped around the graph.

User: "What's in the Dragon Roll and how much does it cost?"

(route → on_topic; retrieve → menu chunks; generate → draft answer; verify → checks that "$18.50," "BBQ freshwater eel," and the other details all appear in the retrieved context. If the draft had invented an ingredient, verify would reject it and the graph would try once more with that feedback.)

The trade-off: each answer now costs at least three LLM calls (route, generate, verify) instead of one. In return, the engine catches its own unsupported answers before the guest sees them.

Planned: Multi-Agent Engines (F14, F15)

The factory was designed so more engines can plug in the same way. Two are on the roadmap but not started:

  • F14 — CrewAI Multi-Role Engine: role-based agents (for example, a menu expert and a policy expert) delegating tasks to each other.
  • F15 — AutoGen Multi-Agent Engine: agents that reach an answer through a back-and-forth conversation.

When they're built, each will be one new class behind BaseMenuEngine and one new branch in get_engine(). The APIs and the evaluation harness won't need to change.

What's next (not yet built): the CrewAI and AutoGen engines, and an engine dropdown in the web UIs. None of these is implemented in this project yet.
