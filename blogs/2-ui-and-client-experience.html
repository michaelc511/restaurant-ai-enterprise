From Idea to Interface: Scoping the App and Putting a Face on the API

Category 2: UI & Client Experience (#ui, #client). Features covered: F0 (App Idea & Scope Design), F5 (Interactive Web Interfaces).

An AI assistant is only useful if someone can actually talk to it. This post covers the two ends of that story: the written idea that defined what the app should do (F0), and the two web interfaces that let a real person use it without touching curl (F5).

Part 1: The App Idea and Scope (F0)

F0 isn't code. It's the written proposal in project-notes.txt (the INTRODUCTION section) that every other feature builds on.

The problem: a general-purpose LLM knows nothing about a specific restaurant. Ask it about "the Dragon Roll" and it can only guess at the price and ingredients — and a confident wrong guess about an ingredient is worse than no answer at all.

The proposed fix: a Retrieval-Augmented Generation (RAG) pipeline. Chunk the restaurant's PDF menus, embed the chunks, retrieve the most relevant ones for each question, and have the LLM answer only from what was retrieved. The menu, not the model's general knowledge, becomes the source of truth.

The scope: three restaurants, each with its own PDF menu — sushi, steak, and italian — and questions about dishes, prices, ingredients, and restaurant policies. That scope is visible all the way through the code: every API and UI offers exactly those three cuisines.

Part 2: Two Web Interfaces on One API (F5)

JSON responses are fine for developers, but a guest needs a text box and a button. F5 adds two browser front ends in the web-demo/ folder:

  • web-demo/gradio_app.py — a Gradio Blocks app.
  • web-demo/streamlit_app.py — a Streamlit app.

Both do the same thing, on purpose. Neither one talks to the RAG chain directly; both send HTTP requests to the FastAPI backend at http://127.0.0.1:8000. Building two different UI frameworks against the same API proves that the API is a real, reusable contract and isn't accidentally tied to one frontend.

What each UI offers

  • Ask a question: pick a cuisine from a dropdown, type a question (pre-filled with "What rolls are on the menu?"), and click Ask. The UI shows the answer and the Top Matching Chunk, the piece of the menu the answer was based on.
  • Debug metrics: when the server includes usage data in its response, a panel shows that call's tokens and cost, plus the session's running totals from the database.
  • Get Daily Specials: calls GET /specials directly. Specials come from a live Google Sheet, not the PDF menu, so this button never touches the RAG chain.
  • Get Today's Hours: sends "What are your hours today?" through POST /ask. Regular hours live in the PDF menu, so this needs the RAG chain; any holiday or event exceptions from the Google Sheet are appended to the answer.

Guest picks sushi and types: "How much is valet parking?"

Answer: "Valet parking is a $12 flat fee…"

(The Top Matching Chunk box underneath shows the parking-policy text from the sushi menu PDF, so the guest — or a developer — can see where the answer came from.)

Running it

uvicorn menu_api:app --reload        # terminal 1: the API
python web-demo/gradio_app.py        # terminal 2: Gradio (opens a browser tab)
streamlit run web-demo/streamlit_app.py   # or Streamlit instead

Current Limitations

  • Every UI user shares one conversation. Neither UI sends a session_id, so every request uses the API's default session. Two people using the Gradio page at the same time share the same chat memory and the same cost totals.
  • No engine picker. The project has a second API entry point that can switch between a plain RAG engine and a LangGraph engine per request, but neither UI exposes that choice yet.
  • Local-only setup. The API address is hard-coded to 127.0.0.1:8000, which is right for a demo but would need to be configurable for a real deployment.

What's next (not yet built): generating a unique session ID per browser tab, adding an engine dropdown, and reading the API address from configuration. None of these is implemented in this project yet.
