Knowing What Every AI Answer Costs: In-Code Token Accounting and a Durable Cost Ledger

Category 5: FinOps & Governance (#finops, #governance, #audit). Features covered: F6 (Token & Cost Accounting), F11 (Relational DB usage ledger).

Every question a guest asks costs real money: tokens in, tokens out, billed per call. A demo can ignore that. A business can't — it needs to know what each answer cost, which session spent it, and whether the monthly bill matches actual usage. This post covers how the project measures cost on every call (F6) and records it permanently (F11).

Step 1: Measure Every Call in Code (F6)

F6 lives in core/telemetry.py. Its core is a small context manager wrapped around each LLM call:

with track_usage(session_usage_totals) as cb:
    result = chain.invoke(...)
usage = UsageInfo(
    prompt_tokens=cb.prompt_tokens,
    completion_tokens=cb.completion_tokens,
    total_tokens=cb.total_tokens,
    total_cost_usd=cb.total_cost,
)
  • The counter: track_usage() uses LangChain's get_openai_callback(), which captures the token counts and estimated dollar cost of every OpenAI call made inside the with block — including nested calls inside chains.
  • The typed record: UsageInfo is a Pydantic model with four fields: prompt tokens, completion tokens, total tokens, and total cost in USD. Using a typed model means the API response and the database both get the same validated shape.
  • The running total: each call's numbers are also added to an in-memory totals dictionary for the running process.
  • Visible in every response: /ask returns a usage field, and the Gradio and Streamlit UIs display it in a Debug Metrics panel.

Two separate switches

  • METRICS (default on) controls whether tracking and persistence happen at all.
  • DEBUG_MODE (default on) only controls whether the numbers are printed to the console.

Keeping these separate means you can turn off noisy console logs in production without losing the cost records.

Console output after a question (with both switches on):

[F6] Tokens - prompt: …, completion: …, total: … | Cost: $…

(Exact numbers vary per question and model; the point is that every call reports its own cost the moment it finishes.)

F6's limitation: the running totals live in a Python dictionary in RAM. Restart the server — a deploy, a crash — and every total resets to zero. The code also notes it isn't thread-safe under concurrent requests, which is fine for this single-worker demo but not for a multi-worker production deployment.

Step 2: A Durable Cost Ledger in SQLite (F11)

A number that disappears on restart isn't an accounting system; it's a scoreboard. F11 (core/database.py) gives every AI call a permanent row in a SQLite database file, usage.db, using Python's built-in sqlite3 — no new dependency and no database server to run.

  • The ledger — the usage_log table: one row per call, with a UTC timestamp, cuisine, session ID, the question, and the full token and cost breakdown. Rows are only ever added, never overwritten.
  • The recorder — log_call(): takes the same UsageInfo object F6 already built and inserts it. Cost is calculated once and used twice: in the API response and in the database.
  • The auditor — get_session_totals(): computes a session's totals on demand with a single SQL SUM() over its rows. There's no second "totals" table to drift out of sync with the raw log, so there's exactly one source of truth.
  • Safe startup: init_db() uses CREATE TABLE IF NOT EXISTS, so it runs on every start without harm.

Since F11, the session_totals field in every /ask response comes from the database, not from F6's in-memory dictionary — so totals survive restarts.

User types: tt

Answer: the session's durable totals from usage.db — prompt tokens, completion tokens, total tokens, and total cost.

(tt is a built-in shortcut in both the API and the terminal loop. It skips the LLM entirely and just reads the ledger, so checking your spend costs nothing.)

What about "Text-to-SQL"?

F11's roadmap name includes "Text-to-SQL Tool," but what's implemented today is the usage ledger only. There's no component yet that turns a natural-language question into a SQL query. The code describes the table as giving "future text-to-SQL tooling a real table to query" — the data is ready; the tool isn't built.

Why This Counts as Governance

  • Accountability: every call is tied to a session, a cuisine, and the exact question asked.
  • Reconciliation: the ledger can be summed by session, by cuisine, or by date and compared against the provider's bill.
  • Audit trail: rows are timestamped in UTC and append-only, so the history of spend can't silently change.

What's next (not yet built): a Text-to-SQL tool that answers questions like "What did the sushi menu cost us last week?" directly from usage_log, and per-session budget limits. Neither is implemented in this project yet.
