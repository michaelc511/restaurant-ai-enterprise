From Notebook to API: Building the Core Runtime of a Restaurant AI Assistant

Category 1: Core Runtime & API (#runtime, #api). Features covered: F1 (Prototype Execution), F2 (Dynamic LLM Selector), F4 (FastAPI Asynchronous Backend).

Every AI feature in this project — memory, re-ranking, guardrails, multi-engine orchestration — runs on top of one small foundation: a model that can be reached, and an API that can be called. This post covers how that foundation was built in three steps: prove the idea in a notebook (F1), make the model provider swappable and verifiable (F2), and serve it over HTTP (F4).

Step 1: Prove the Idea in a Notebook (F1)

Before building a web server, a database, or a UI, one question needed an answer as cheaply as possible: can an LLM answer questions correctly if you just hand it the right document?

The prototype, prototype/Demo_01_Building_a_RAG_Powered_FAQ_Agent_with_Custom_Knowledge.ipynb, answers that in nine notebook steps:

  • Load an FAQ text file with TextLoader and split it into 500-character chunks with a 50-character overlap (CharacterTextSplitter).
  • Embed the chunks with Azure OpenAI's text-embedding-ada-002 and store them in a FAISS vector index.
  • Connect an Azure OpenAI chat model and wire everything into LangChain's RetrievalQA chain with return_source_documents=True.
  • Ask one question ("What is our return policy?") and print the answer next to the source chunks it came from.

There's no error handling, no server, and no UI — on purpose. The notebook's only job was to show the approach works. Once it did, the same pattern was rebuilt for restaurant menus: PyPDFLoader reading menus/sushi.pdf, steak.pdf, and italian.pdf instead of a text file, first as menu_rag.py and then as menu_api.py.

Step 2: Make the Model Provider Swappable and Verifiable (F2)

The app can run on two providers: OpenAI directly, or Azure's hosted OpenAI. Which one it uses is decided by which API key is present in .env:

if os.environ.get("OPENAI_API_KEY"):
    llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)
    embeddings = OpenAIEmbeddings(model="text-embedding-3-small")
elif os.environ.get("AZURE_OPENAI_API_KEY"):
    llm = AzureChatOpenAI(..., deployment_name="gpt-5-mini", temperature=0)
    embeddings = AzureOpenAIEmbeddings(..., deployment="text-embedding-ada-002")
else:
    raise RuntimeError("Set OPENAI_API_KEY or AZURE_OPENAI_API_KEY in the .env file")
  • OpenAI first, Azure as a fallback. OpenAI was made the default so the project runs on its own, without depending on a class lab's Azure gateway.
  • temperature=0 on both branches. A restaurant assistant should give the same price for the same dish every time, so answers are kept deterministic and focused.
  • Fail fast with no key. If neither key is set, the app refuses to start with a clear error instead of failing later on a customer's first question.
  • A connectivity check at startup. When DEBUG_MODE is on, menu_api.py prints which provider it picked and sends a plain test prompt ("Say 'connection ok' if you can read this.") before building any indexes. A bad or expired key shows up immediately, not halfway through embedding a menu.

Later, this selection logic was extracted into core/llm.py as build_llm_and_embeddings(), so every engine shares one copy instead of duplicating it. menu_api.py deliberately keeps its own inline copy so it stays runnable as a standalone baseline.

What F2 isn't (yet): the selector chooses between two flavors of OpenAI models. Other vendors such as Ollama, Gemini, or Claude aren't wired in today.

Step 3: Serve It Over HTTP (F4)

menu_api.py turns the RAG pipeline into a FastAPI app:

uvicorn menu_api:app --reload
  • Build once, reuse forever. At startup, a RAG chain is built for each of the three cuisines (sushi, steak, italian) and kept in a dictionary. FAISS indexes are loaded from the vectorstores/ folder if they already exist, so restarts don't re-embed every menu.
  • POST /ask takes {"cuisine": "sushi", "question": "...", "session_id": "..."} and returns the answer plus top_match, the menu chunk that best supported it. When metrics are on, the response also includes token usage, session cost totals, and a latency breakdown.
  • GET /specials and GET /hours expose live restaurant-ops data from a Google Sheet.
  • Validated input. The request body is a Pydantic model (AskRequest), and an unknown cuisine gets a clear error listing the valid choices.
  • Two ways to run. uvicorn serves the API; running python3 menu_api.py directly starts an interactive terminal loop with the same pipeline.

Request: POST /ask {"cuisine": "sushi", "question": "Is there a corkage fee if I bring my own wine?"}

Answer: "Yes, the corkage fee is $30 per 720ml bottle."

(The top_match field in the same response shows the menu-policy chunk the answer came from, so you can see why the model said it.)

A note on "asynchronous": the route handlers are written as regular def functions, not async def. FastAPI runs plain def handlers in a worker thread pool, so a slow LLM call doesn't block the server's event loop. The responses aren't streamed; each answer is returned in one piece when it's ready.

The repo also includes flask_app.py, a minimal Flask version of /ask that reuses the same chains. It's a useful side-by-side comparison, but FastAPI is the main backend that every later feature builds on.

Why This Foundation Matters

Each later feature plugs into one of these three pieces: the shared provider selection (F2), the per-cuisine chains built at startup, or the /ask request flow (F4). Because the API contract — cuisine and question in, answer and evidence out — stayed stable, two different web UIs, a second API entry point, and an evaluation harness could all be added later without rewriting it.

What's next (not yet built): streaming responses token by token, true async handlers, and additional model providers would each be natural upgrades to this runtime. None of them is implemented in this project yet.
