Architecting Adaptive Conversational Memory: From Ephemeral Buffers to Durable SQL Checkpoints

Memory — How Agents Remember

Sensory Memory

The immediate, transient input processed by an agent during a single step of execution.

Example: An agent briefly holds the raw error message returned by a failed shell command while formulating its next attempt.

Working Memory

The active context window holding current conversation history, active workspace data, and immediate scratchpad notes.

Example: An agent references recent user instructions stored in the current prompt history to maintain conversational continuity.

Vector DBs / SQL DBs

Episodic Memory

An external storage system that records historical events, past interactions, and previous task outcomes for long-term recall.

Example: A coding agent checks its past execution logs to see what unit tests failed during yesterday's build attempt.

Semantic Memory

Persistent storage containing enduring domain knowledge, learned operational rules, and user preference profiles.

Example: An assistant retrieves a stored preference rule stating that a specific user always requires responses formatted in markdown tables.

What Our Blog Will Focus On

These four memory types cover how AI agents hold on to information. Our architecture and this post focus on the two that handle live dialogue and session state:

Working Memory & Episodic Memory (our main focus): We implement these through two features. The first is ephemeral in-RAM chat history (F7), which keeps the working context of the current conversation. The second is persistent SQLite-backed chat history (F16), which keeps a session's episode of the conversation even if the server restarts. Both are built on LangChain's chat-history classes, wrapped in RunnableWithMessageHistory.

Semantic Memory (via RAG): Our retrieval pipeline provides this. Vector search (F3), hybrid BM25 + FAISS fusion (F18), and cross-encoder re-ranking (F10) ground the assistant in lasting domain knowledge: the restaurant menus.

When you deploy a generative AI app to production, treating every user query as a separate event makes for a bad experience. Without conversational memory, the assistant has "amnesia" and users must repeat themselves on every turn.

Our roadmap fixes this in two steps. We start with ephemeral in-memory history (F7), then add an opt-in persistent SQL backend (F16) behind the same interface.

Phase 1: Short-Term Context with Ephemeral Chat Memory (F7)

Large Language Models are stateless: each request starts from scratch. F7 fills that gap without any outside infrastructure. All of it lives in one module, core/memory.py.

  • Storage: a module-level dictionary (_session_histories) maps each session ID to a LangChain ChatMessageHistory object that lives entirely in RAM.
  • Session isolation: session keys include the cuisine (f"{cuisine}:{session_id}"), so one customer's sushi conversation never mixes with another customer's, or with their own conversation about a different cuisine.
  • Wiring: wrap_with_memory() wraps each RAG chain in LangChain's RunnableWithMessageHistory. It loads the session's history before each call and records the new question and answer afterward.
  • Context injection: _render_history() formats the recent turns as a plain-text "Previous conversation:" block and puts it in front of the user's question. Because the question carries the history with it, the history affects both retrieval and the generated answer.
  • Sliding window: only the last MAX_HISTORY_TURNS = 5 exchanges are included in the prompt, which keeps token cost under control.
  • Both engines share it: the plain RAG engine and the LangGraph engine (F13) both use wrap_with_memory, so they behave the same way with memory.

How it works, with an example:

User: "Which appetizers are gluten-free?"

Answer: "The Sea Salt Edamame ($6.50) and the Hamachi Jalapeño Crudo ($16.50)."

User: "How much is the second one?"

Answer: "The Hamachi Jalapeño Crudo is $16.50."

(F7 put the previous exchange in front of the question, so the model knew what "the second one" meant.)

A deliberate exception: hours questions skip memory (F8). Questions about opening hours are answered with no history at all. If earlier turns about rolls or prices were added to the query, they could pull retrieval toward the wrong documents.

Limitations of Phase 1:

Example of the sliding window cutoff:

User (Turn 1): "Just so you know, I have a severe peanut allergy."

Answer (Turn 1): "Understood. I'll keep that in mind."

[... Turns 2–6 cover rolls, sides, and drinks ...]

User (Turn 7): "Is the dessert we talked about safe for me?"

Answer: "Could you tell me which allergies or ingredients you're concerned about?"

(At Turn 7, the 5-exchange window holds only Turns 2–6, so the allergy from Turn 1 is no longer in the prompt.)

Example of process volatility:

User: "Which of your rolls are spicy?"

Answer: "The Spicy Tuna Volcano Roll and the Spicy Scallop Hand Roll."

[... The uvicorn server restarts during a routine deployment ...]

User: "Is the first one gluten-free?"

Answer: "Could you clarify which item you mean?"

(The history lived only in a RAM dictionary inside the process, so the restart erased every active session.)

Phase 2: Durable SQLite Chat History (F16)

F7 has one major weakness: volatility. If the process restarts because of a deployment or a container crash, every customer's conversation disappears.

F16 (Persistent Thread Checkpointing) fixes this with an opt-in backend switch in the same file:

MEMORY_BACKEND = os.environ.get("MEMORY_BACKEND", "ephemeral").lower()
CHAT_HISTORY_DB_PATH = "chat_history.db"

def get_session_history(session_id: str) -> BaseChatMessageHistory:
    if MEMORY_BACKEND == "persistent":  # F16: durable, survives a restart/crash
        return SQLChatMessageHistory(session_id=session_id, connection=f"sqlite:///{CHAT_HISTORY_DB_PATH}")
    if session_id not in _session_histories:  # F7: ephemeral (default)
        _session_histories[session_id] = ChatMessageHistory()
    return _session_histories[session_id]

What changed and what didn't:

  • Same interface: get_session_history() still returns a LangChain BaseChatMessageHistory. With MEMORY_BACKEND=persistent it returns LangChain's SQLChatMessageHistory, which writes to chat_history.db on disk. RunnableWithMessageHistory, wrap_with_memory(), both engines, the API routes, and the frontend needed no changes.
  • Opt-in: the default is still ephemeral (F7). Persistence is enabled with an environment variable.
  • Trim when building the prompt, not when storing: F16 also made the stored history complete in both modes. The 5-exchange sliding window is applied only when the history is rendered into the prompt, so the full conversation stays stored while each LLM call stays the same size.
  • Not a LangGraph checkpointer: despite the feature's name, F16 uses LangChain's SQL chat-message history, not LangGraph's SqliteSaver. The F13 LangGraph engine's GraphState holds per-request state only, and its conversation memory still comes from this module.

How this improved the product:

Example of crash recovery:

User: "Which of your rolls are spicy?"

Answer: "The Spicy Tuna Volcano Roll and the Spicy Scallop Hand Roll."

[... The uvicorn server restarts during a rolling deployment ...]

User: "Is the first one gluten-free?"

Answer: "The Spicy Tuna Volcano Roll isn't listed as gluten-free. It's topped with crispy tempura flakes."

(Each exchange was written to SQLite as it happened. After the restart, SQLChatMessageHistory reloaded the session's history from disk, so "the first one" still meant the Spicy Tuna Volcano Roll.)

Example of no downstream changes:

The same session_id the frontend already sends now maps to a durable conversation. This needed no change to API route logic or UI components, only MEMORY_BACKEND=persistent.

(Note: per-session token and cost totals come from F11's separate usage.db log. They aren't part of conversational memory.)

What's next (not yet built): One fixed window isn't ideal for every situation. Possible future upgrades include a token-based limit instead of a turn count, or summarizing older turns so key facts like an allergy aren't dropped. Neither is implemented in this project yet.
