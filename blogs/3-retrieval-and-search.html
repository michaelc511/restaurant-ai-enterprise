Finding the Right Menu Facts: Vector Search, Prompt Grounding, Re-ranking, and Hybrid Fusion

Category 3: Retrieval & Search (#rag, #search, #retrieval). Features covered: F3 (Semantic RAG & Vector Store), F3.1 (RAG System Prompt & Persona), F10 (FlashRank Cross-Encoder Re-ranking), F18 (Hybrid Search Fusion).

A RAG assistant can only be as good as the context it's handed. If the chunk with the right price never reaches the model, no amount of prompting will produce the right answer. This post walks through the retrieval pipeline in the order it was built, and the order a question flows through it today.

question
  ├─▶ BM25 keyword search  (F18) ─┐
  └─▶ FAISS vector search  (F3)  ─┴─▶ fuse (F18) ─▶ re-rank top 3 (F10) ─▶ prompt with persona (F3.1) ─▶ answer

Step 1: Semantic RAG and the Vector Store (F3)

  • Load: PyPDFLoader reads menus/<cuisine>.pdf.
  • Chunk: RecursiveCharacterTextSplitter splits it into chunks of up to 500 characters with a 50-character overlap, so a dish description that straddles a boundary isn't cut in half with no context.
  • Embed and index: each chunk is embedded and stored in a FAISS index.
  • Cache to disk: the index is saved to vectorstores/<cuisine>. On the next start it's loaded instead of rebuilt, which skips the expensive embedding API calls.
  • Answer with evidence: LangChain's RetrievalQA chain runs with return_source_documents=True, so every answer comes back with the chunks it was based on.

Vector search matches by meaning. "Anything without meat?" can find a chunk that says "Vegan" even though the words don't overlap.

Step 2: A System Prompt That Keeps Answers Grounded (F3.1)

Retrieval decides what the model sees; the system prompt decides how it uses it. F3.1 replaced RetrievalQA's generic default prompt with a ChatPromptTemplate built from a system message and a human message. The system prompt sets:

  • A persona: "a friendly, knowledgeable restaurant assistant."
  • A hard grounding rule: answer using ONLY the given context, and never invent dishes, prices, ingredients, allergens, or policies.
  • An honest fallback: if the answer isn't in the context, say so plainly ("I don't have that information") instead of guessing.
  • Style rules: keep answers concise and conversational, mention prices when referencing dishes, and state specific policy details (fees, time limits, exceptions) rather than vague paraphrases.
  • Date awareness: if a question mentions "today," "Friday," or "this weekend," use that to pick the right part of the context.

User: "What's in the Dragon Roll and how much does it cost?"

Answer: "The Dragon Roll ($18.50) has BBQ freshwater eel and crisp cucumber inside, topped with thinly sliced avocado, sweet unagi glaze, and toasted sesame seeds."

(The price is included because the prompt asks for it, and every detail comes straight from the retrieved menu chunk.)

Step 3: Cross-Encoder Re-ranking (F10)

FAISS ranks chunks by vector similarity, which is fast but approximate. The chunk that truly answers the question isn't always ranked first.

F10 adds a second stage in core/vectorstore.py. A RerankingRetriever wraps the base retriever, takes its candidates, and re-scores each one against the question using FlashRank's ms-marco-MiniLM-L-12-v2 cross-encoder. Only the top 3 go on to the LLM.

  • Why a cross-encoder? A vector search compares two embeddings made separately. A cross-encoder reads the question and the chunk together, so it judges relevance much more precisely — too slowly to search a whole menu, but fast enough to re-sort a handful of candidates.
  • Small and local: FlashRank runs on the CPU with no extra API calls or cost.

Step 4: Hybrid Search with BM25 + FAISS (F18)

Vector search has a blind spot: exact terms. A dish name, a price, or an allergen word can get blurred together with similar-sounding text in embedding space. Classic keyword search doesn't have that problem.

F18 adds BM25 (Best Matching 25), a keyword-ranking algorithm that scores chunks by how often the question's exact words appear in them, weighted by how rare those words are. In get_retriever():

faiss_retriever = vectorstore.as_retriever(search_kwargs={"k": top_k})  # meaning
bm25_retriever = BM25Retriever.from_documents(docs)                     # exact words
bm25_retriever.k = top_k

hybrid_retriever = EnsembleRetriever(
    retrievers=[bm25_retriever, faiss_retriever], weights=[0.5, 0.5]
)
return wrap_with_sanitization(wrap_with_reranking(hybrid_retriever, top_k=top_k))
  • Reciprocal rank fusion: EnsembleRetriever merges the two ranked lists, giving equal weight to each. A chunk ranked highly by either search makes it into the candidate pool.
  • Then re-ranked: the merged candidates go through F10's cross-encoder, which picks the final top 3.
  • No extra index on disk: BM25 is rebuilt in memory from the PDF's chunks on each start. Parsing the PDF is cheap and local; the expensive FAISS embeddings are still cached.

User: "How much is the Saba Shioyaki?"

(An unusual name like "Saba Shioyaki" is exactly where BM25 helps: the keyword search matches the exact words, even if the vector search ranks a different grilled-fish chunk higher.)

Where hybrid search applies: F18 lives in the shared get_retriever() used by the engine-based API (engine_api.py) and the evaluation harness. The original menu_api.py is kept unchanged as a baseline and still uses FAISS-only retrieval with F10 re-ranking.

Retrieval Quality Is Measurable

Each of these upgrades changes what the model sees, so each one needs to be checked, not assumed. The project's evaluation suite scores every answer for context precision — how many of the retrieved chunks were actually useful — alongside faithfulness and relevancy. That turns "did re-ranking help?" into a number instead of a feeling.

What's next (not yet built): tuning the 50/50 BM25-to-FAISS weighting per cuisine, and bringing hybrid search into menu_api.py. Neither is implemented in this project yet.
