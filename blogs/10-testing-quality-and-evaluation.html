Turning "Did That Change Help?" Into a Number: Unit Tests, LLM-Judged Evals, and a CI Gate

Category 10: Testing, Quality & Evaluation (#eval, #testing, #cicd). Features covered: F23 (Unit Tests for Core Modules), F17 (Automated RAG Evaluation Suite), F20 (CI/CD Eval Regression Gate).

An AI app can break in two very different ways. The code can be wrong — a function returns the wrong value. Or the code can be fine while the answers get worse — a prompt tweak makes the model start inventing prices. Each needs its own kind of test. This post covers both, and the pipeline that runs them automatically on every pull request.

Layer 1: Unit Tests for the Logic (F23)

The tests/ folder holds 58 pytest tests across six modules:

  • test_database.py — the cost ledger: table creation, safe re-runs, row inserts, per-session sums, and that one session's totals never leak into another's. Each test uses a temporary database file.
  • test_sheets.py — the Google Sheets logic: date phrases ("tomorrow," "in 3 days," "this weekend," weekday names), specials-vs-hours keyword routing, active-row filtering, and error wrapping — all against fake sheet objects.
  • test_vectorstore.py — re-ranking order and top_k, and that the retriever fuses BM25 with FAISS and builds an index when one is missing.
  • test_sanitize.py — that chunks are wrapped in delimiters and forged delimiter tags are stripped.
  • test_guardrails.py — the intent classifier's structured-output call and its off-topic check.
  • test_evaluation.py — the eval scoring and pass/fail thresholds themselves.

Fully mocked: no test needs an API key or a network connection. LLM calls, the cross-encoder, and Google Sheets are replaced with fakes. The suite runs in under a second and costs nothing.

Layer 2: LLM-Judged Evaluation of Real Answers (F17)

Unit tests can't tell you whether an answer is good. F17 (evaluation/) runs real questions through the real system and has an LLM grade the results.

Fixed test questions

Each cuisine has a checked-in fixture file (evaluation/fixtures/sushi.json, steak.json, italian.json) with five questions and their known-good answers — 15 in total. Because the questions never change, a score change means the system changed, not the test.

Three scores per answer

  • Faithfulness (must be ≥ 0.8): is every claim in the answer supported by the retrieved context? Adding a price or ingredient that isn't there fails, even if it happens to be true.
  • Answer relevancy (≥ 0.8): does the answer actually address the question?
  • Context precision (≥ 0.6): how many of the retrieved chunks were actually useful? The lower bar tolerates some noise.

A question passes only if all three meet their thresholds.

How it's built

  • Same factory as production: questions go through get_engine(...), so the eval tests exactly what users hit. --engine langgraph and --cuisine sushi select what to test.
  • Structured judging: each metric is one llm.with_structured_output(MetricJudgment) call returning a 0.0–1.0 score and a short reason.
  • Memory off: every question is answered with use_memory=False, so leftover conversation from a previous fixture can't affect the score.
  • Why not Ragas or DeepEval? Installing Ragas in this environment would downgrade the openai and langchain-openai packages that every engine depends on. Scoring the same three metrics with the already-installed LLM avoids the conflict.
  • A pass/fail exit code: the script exits with 0 if every question passed and 1 otherwise — exactly what CI needs.
python -m evaluation.run_evals
[PASS] What's in the Dragon Roll and how much does it cost?
    faithfulness=…  answer_relevancy=…  context_precision=…
…
15/15 passed

(Scores vary by run; for any FAIL line, the judge's reasoning for each metric is printed underneath.)

One nuance: the fixtures store an expected answer for each question, but the three judges don't compare against it — they grade the answer against the question and the retrieved context. The expected answers serve as a human reference for now.

Layer 3: Enforce It on Every Pull Request (F20)

An eval suite nobody runs doesn't protect anything. F20 (.github/workflows/eval_gate.yml) is a GitHub Actions workflow that runs on every pull request to main (and on demand):

  1. unit-tests installs dependencies on Python 3.11 and runs pytest. It needs no secrets, so it runs on every PR, including ones from forks.
  2. eval-gate runs only after unit tests pass — if the code is broken, the eval numbers can't be trusted either. It runs python -m evaluation.run_evals against the real OpenAI API using the repository's OPENAI_API_KEY secret, and fails the build if any question drops below its thresholds.
  • Fork safety: GitHub never exposes a repository's secrets to workflows triggered by fork PRs, so the eval job is skipped for them instead of failing.
  • Built from scratch every time: the vectorstores/ cache isn't committed, so CI builds fresh FAISS indexes from the PDFs on each run — the eval tests the full pipeline, not a stale index.

The Result

A change now has to pass two bars before it merges: the code does what it says (F23), and the answers are still grounded, relevant, and well-retrieved (F17), checked automatically (F20). "Did that prompt tweak help or hurt?" has a number for an answer.

What's next (not yet built): comparing answers against the stored expected answers, running the eval gate against the LangGraph engine as well, and unit tests for the memory and telemetry modules. None of these is implemented in this project yet.
